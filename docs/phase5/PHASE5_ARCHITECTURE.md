# PHASE 5 — BEHAVIOR RECOGNITION ENGINE

## Approved seven-node structure

| Node | Component | Responsibility |
|---|---|---|
| 5.1 | BehaviorInputAdapter | Convert source observations to the behavior contract |
| 5.2 | FeatureExtractor | Extract analyzable features |
| 5.3 | TemporalStateManager | Maintain per-track temporal history |
| 5.4 | BehaviorPlugin Registry | Register and manage independent plugins |
| 5.5 | Rule Engine | Evaluate behavior rules and thresholds |
| 5.6 | Event Manager | Manage event lifecycle |
| 5.7 | BehaviorResult | Produce standardized output |

## Initial behavior plugins

- PhoneUsagePlugin
- InactivityPlugin
- GatheringPlugin

These plugins are separate from the seven architectural nodes.
They are registered and managed by node 5.4.

## Node 5.1 — BehaviorInputAdapter

### Purpose

Convert existing vision observations into an independent,
validated BehaviorFrame contract.

### Accepted input sources

1. Existing `company_vision.core.schemas.FrameResult`.
2. Neutral tracking-output records containing person observations.

The adapter must not import or execute YOLO, Dahua SDK,
GPU inference, camera capture or tracker implementations.

### Output

`company_vision.behaviors.schemas.BehaviorFrame`

### Contract fields

- schema_version
- camera_id
- session_id
- frame_id
- timestamp_utc
- monotonic_timestamp
- width / height
- persons
- objects
- object_detection_status
- track_lifecycle_events
- source
- source_status

### Person observation

- track_id
- bbox
- confidence
- keypoints
- raw_keypoints
- keypoint_weights
- observed
- predicted
- behavior_eligible
- track_lifecycle
- missed

### Important constraints

- No fixed maximum person count.
- Track IDs are preserved, not generated by the adapter.
- Session ID is supplied by the caller; it is never fabricated.
- UTC and monotonic timestamps are not synthesized.
- Predicted tracks are not automatically behavior-eligible.
- Eligibility requires explicit observed evidence.
- Missing object detection is represented as not_run or unavailable.
- Invalid or missing keypoints are preserved as invalid/unknown.
- No behavior classification occurs in this node.
- Existing phase 1-4 contracts and algorithms remain unchanged.

### Current nine-keypoint mapping

The current live pose path supplies:

1. nose
2. left_eye
3. right_eye
4. left_ear
5. right_ear
6. left_shoulder
7. right_shoulder
8. left_elbow
9. right_elbow

This mapping is a source adapter default, not a restriction
on future behavior input schemas.

### Acceptance tests

- FrameResult conversion
- tracking-output conversion
- variable person count
- identity preservation
- raw and filtered keypoint preservation
- weight preservation
- observed/predicted distinction
- empty frames
- duplicate identity rejection
- frame-bound validation
- UTC timestamp validation
- metadata validation
- object observation preservation
- eligibility validation

## Execution boundaries

Node 5.1 performs input conversion and validation only.

Feature calculation belongs to node 5.2.
Temporal history belongs to node 5.3.
Plugin registration belongs to node 5.4.
Rule evaluation belongs to node 5.5.
Event lifecycle belongs to node 5.6.
Final output formatting belongs to node 5.7.
